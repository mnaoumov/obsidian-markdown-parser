## Re-reading every oracle from another Obsidian

```sh
npm run oracle:refresh -- [--obsidian-version <x.y.z|public-latest|catalyst-latest>] [--out-dir <directory>] [--only classes,spec,quirk-probes,forum-issues,editing-modes,live-surfaces,link-parity,special-names,link-cases,worker] [--skip-drift] [--skip-differential]
```

It needs a global `obsidian-integration-testing` install, which launches each Obsidian it reads in its own throw-away profile and vault. Without `--obsidian-version` it reads the installed Obsidian.

1. It launches the version once, to learn its exact version number and to take its metadata worker, `worker.js`, from the instance (the app serves it beside its page). The worker goes to a temporary file outside the repository and is deleted when the run ends; none of the app's code is kept.
2. It runs `scripts/capture/oracle.ts` once per pinned seed, with the pinned file's `--per-set`, then `scripts/capture/spec-oracle.ts`, `scripts/capture/quirk-probe-oracle.ts`, `scripts/modes/forum-issue-oracle.ts`, `scripts/modes/editing-modes-oracle.ts`, `scripts/live-surfaces-oracle.ts`, `scripts/links/link-parity-oracle.ts`, `scripts/links/special-names-oracle.ts` (plain and with `--normalization`) and `scripts/links/link-cases-oracle.ts`, each pinned to that exact version, and `scripts/capture/worker-oracle.ts` on the worker it took, with the pinned file's `--per-set` and `--seed`.
3. It writes the files to `oracle/`, named after the version, beside the pinned ones. A re-read of the pinned version itself goes to a temporary directory instead (`<tmp>/obsidian-oracles-<version>`), so it never overwrites the files the suites check against.
4. It runs the drift report below, then the release differential.

A class-span re-read follows the corpus as it is now. Every pinned file holds the current corpus, 4,228 documents per seed: seeds 3141 and 6174 were first read from it, and the other nine were read again from it on 2026-10-22 and replaced. When a piece set is added or grows, that also moves what a seed draws for the sets after it, so most documents of a later re-read have another text under the same id, and the report counts them as new rather than compared until the files are read again.

The editing-mode capture can also run by itself in bounded batches:

```sh
npx jiti scripts/modes/editing-modes-oracle.ts --obsidian-version 1.15.1 --checkpoint <file> --max-documents 100
npx jiti scripts/modes/editing-modes-oracle.ts --obsidian-version 1.15.1 --resume <file> --max-documents 100
```

The limit counts new documents in that invocation. Each completed read replaces the checkpoint atomically. Resuming requires the same app version, browser user agent and exact corpus prefix; the saved readings are kept unchanged. The reader replays the prefix's syntax-tree reads to restore sub-mode initialization order, without repeating its DOM measurements. An incomplete batch writes only its checkpoint; the final oracle is written only after every document has been read. Omit the limit to finish the remainder in one invocation. When an editing-mode capture was completed separately, omit `editing-modes` from a subsequent refresh's `--only` list.

## The drift report

```sh
npm run oracle:drift -- --to-version <version> [--to-dir <directory>] [--from-version <version>] [--from-dir <directory>] [--examples <n>] [--skip-tests]
```

It compares each oracle of one version (by default the pinned one, in `oracle/`) with the same oracle of another. A document is matched across the two by its source: a class-span document by its id and the text it was built as, a spec example by its number and markdown, a probe by its markdown, a worker document by its set and text. Per oracle it prints:

- **compared**: the documents both versions read from the same source.
- **changed**: those whose reading differs between the versions, with the first few named.
- **new**: those only the newer read holds.
- **parser exact**: on the editor's classes (every class-span document and spec example) and on the whole `CachedMetadata` (every worker document and spec example), how many the parser matches on each version, and the documents it matches on the older version only.

Then it runs the suites that check the parser against Obsidian (`highlight`, `language`, `editing-modes`, `forum-issues`, `spec-quirks`, `quirk-probes` and `worker-metadata`) on the newer version's files, by setting `ORACLE_OBSIDIAN_VERSION` and `ORACLE_DIRECTORY`. That covers what the report does not score itself: the reading view's HTML of the spec examples and the probes, and every quirk the suites explain. A suite whose files the newer version lacks is skipped, and the report names the missing file, so a partial re-read (`--only`) runs only the suites it read for; none is run against another version's files, because a pass would then say nothing about the newer one. It exits 1 when the parser newly differs anywhere or a suite it ran fails.

The parser's score is shown on both versions because it is not 100% everywhere on the pinned one: 13 spec examples differ in the editor's classes on 1.14.5, 1.15.0 and 1.15.1. A new version is judged by what it changes, not by that baseline.

## The release differential

```sh
npm run oracle:differential -- --to-version <version> [--to-dir <directory>] [--from-version <version>] [--from-dir <directory>] [--out-dir <directory>]
```

The drift report asks whether the parser still matches a new build. The differential asks what the build changes in the bugs the judges find ([`mode-judge.md`](mode-judge.md), [`self-check.md`](self-check.md#a-new-obsidian-build)): a family appearing is a new candidate, one vanishing may be a fix to confirm and close on the forum, and a count moving is a family growing or shrinking. `scripts/oracles/release-differential.ts` runs, once per version in a child process pointed at that version's files by `ORACLE_OBSIDIAN_VERSION` and `ORACLE_DIRECTORY`:

- **The mode judge** on the class-span trees, spec examples and worker documents. Its editor side is the build's own trees; the spec examples and worker documents are judged on the class tokenizer's prediction for that version.
- **The live surface judges** on the build's live surface oracle (`self-check --count 0 --live-surfaces`).

A judge whose oracle either version lacks is skipped, and the report names the missing file, so a partial re-read (`--only`) still gives the tables it can. Each table names how many documents it judged on each version. When those differ, the corpus moved under the oracles, and a count can move with it rather than with the build: the drift report's `new` column says which documents. It writes `report.md`, and each version's raw `mode-judge.json` and `self-check.json` under `from/` and `to/`, to `dist/release-differential/<from>-to-<to>/`. It is a report, not a gate, and exits 0 unless a judge fails.

Both judges' Reading view side is the `remark-parse` 8 engine, which matches the pinned version. The drift report shows whether a build changed the reading view; until the engine follows such a change, the differential cannot see what it does to the families.

2026-10-25, the first runs. The pinned 1.14.5 against itself moved no family: 45 mode judge families with 9,626 findings over 50,466 documents, and the 8 live surface families with 173 findings over 400 notes, those [`self-check.md`](self-check.md#the-live-surfaces) records. 1.14.4, from the re-read kept in a temporary directory, against 1.14.5 changed 5 mode judge families by 8 findings in all and added or removed none. That came from the corpus, not the build: the class-span corpora of the two are the same texts, but that worker oracle holds 48 documents fewer, so 50,418 were judged. It has no live surface oracle, so that table was skipped.

## Moving to a new Obsidian

1. `npm run oracle:refresh -- --obsidian-version <version>`.
2. Where readings changed, fix the parser until the drift report and the suites are clean on the new files. Read the release differential's report for families that appeared or vanished, and sort each new one into a family, or close its forum topic when one vanished.
3. Change `PINNED_OBSIDIAN_VERSION` to the new version, so the conformance suites and the next report start from it.
4. Re-point what records numbers on particular files rather than checking conformance, and re-record those numbers: the `syntax-score`, `lezer`, `micromark` and `markdown-it` suites and the `adapter-diff`, `cm6-bench`, `oracle-diff` and `syntax-diff` scripts name the pinned version's files themselves. Remove the old files only after that.

## The oracles as test cases for another project

```sh
npm run export:test-cases -- [--out <directory>]
```

writes the pinned spec, quirk probe, metadata worker, forum issue and editing mode oracles as plain JSON into `dist/test-cases/` (`scripts/oracles/export-test-cases.ts`, built by `src/oracle/spec/test-case-export.ts`), with a `README.md` on their format, for a project that keeps them next to its own tests. Every value is the spec's, a reference implementation's or Obsidian's own output, and nothing of this repository's code goes with them. The export empties the folder first, so a file an earlier export wrote under another name cannot linger beside its successor, and refuses to when the folder holds a subfolder or a file other than `*.json` and `README.md`.

An `-all` file holds every case of its source and a `-failing` file only the cases Obsidian does not give the expected output on, the same cases under the same ids. A `-spec` file holds the spec's own examples, whose expected HTML is the spec's; a `-no-spec` file holds documents beyond them, whose expected HTML comes from a reference implementation that passes its whole spec suite. By `editor` we mean `Source mode` or `Live Preview`: the `editor-vs-reading-view` files compare the editor with Reading view, and give each of the two modes its own HTML.

- `commonmark-spec-0.31.2-all.json` and `gfm-spec-0.29.0.gfm.13-all.json`: the 652 CommonMark examples and the 22 GFM extension examples, each with the spec's HTML (`commonMarkSpecHtml`), Reading view's (`obsidianReadingViewHtml`, `strictLineBreaks: true`, and `obsidianReadingViewHtmlSoftBreaksAsHard` on the 66 examples the default `false` changes), the worker's `CachedMetadata`, and the `departures` from `SPEC_DIFFERENCES` on the 261 examples that carry one.
- `commonmark-spec-0.31.2-failing.json` and `gfm-spec-0.29.0.gfm.13-failing.json`: the 205 and 7 cases of those files, unchanged and under the same id, whose `obsidianReadingViewHtml` differs from the spec's: the 212 examples the reading view departs on. The other 49 examples with a `departures` entry carry only `soft line breaks are hard`, so their `obsidianReadingViewHtml` matches the spec and they stay in the full files only. A failing file is the full file filtered by `readingViewDifferences`, never a list of its own, so the two cannot drift.
- `commonmark-no-spec-failing.json` and `gfm-no-spec-failing.json`: the 70 of the 117 CommonMark quirk probes and the 27 of the 52 GFM ones (tables and strikethrough) on which the reading view's HTML differs from the reference implementation's, `referenceHtml`, compared as the spec files compare it with the spec's. Each has the reading view's HTML, the worker's sections and a note on the quirk; the 72 probes on which the two agree are left out. The CommonMark reference is [commonmark.js](https://github.com/commonmark/commonmark.js) 0.31.2, the reference implementation, run in the export. The GFM reference is [cmark-gfm](https://github.com/github/cmark-gfm) 0.29.0.gfm.13, the GFM spec's own implementation, with the extensions the spec's tests use; the JavaScript ports of it are older releases, and micromark's GFM extension departs from the spec on purpose (it links `ftp://` nowhere and autolinks inside `<...>`), so `npm run oracle:reference` (`scripts/capture/reference-oracle.ts`) runs it through the Python `cmarkgfm` binding, with `uv`, into `oracle/reference-cmark-gfm-0.29.0.gfm.13.json`, for every spec example and GFM probe. Run it again when a GFM probe is added or changed. `src/oracle/spec/reference-html.test.ts` checks both before they are trusted: commonmark.js gives the spec's HTML on all 652 CommonMark 0.31.2 examples and cmark-gfm on all 22 GFM extension examples, both exactly. The reference HTML goes through a DOM before the comparison, by `parse5`, which gives the spec oracle's `specDom` on every example but 3 where the app's Chromium keeps a processing instruction or escapes `<` in an attribute, none of which a probe's reference HTML holds.
- `metadata-cache-all.json`: the 3,743 worker documents with the worker's whole `CachedMetadata`, `null` on the 19 the worker throws on.
- `metadata-cache-failing.json`: the 30 notes whose metadata the worker drops or misplaces. First the 19 worker documents it throws on, unchanged and under the same id, each with the forum issue of its trigger, sorted by `workerFailureOf` (`src/metadata/metadata.ts`): each holds a front matter string that is a markdown link with an empty or blank destination (issue 1). Up to 1.15.0 a key `hasOwnProperty` made it throw too (issue 2), on 12 more; 1.15.1 reads it. No stand-in of them was read, so they carry no `expectedMetadata`. Then the 11 samples of the forum issues where the worker still drops or misplaces metadata (issues 1, 3 and 4, and `issue-topic-119821`, reported after the summary), with the worker's `CachedMetadata` (`null` on the 2 where it throws) and, on 7 of them, `expectedMetadata`: for 1 the worker's metadata of a stand-in note of the same length without the trigger, the property put back; for 3 the worker's own metadata without the two zero-length sections, the block id on the footnote definition; for topic 119821 the worker's own metadata with the link on a `%%` block comment's opening line, or on a callout's unindented `>` line in a list item, moved to where its `[[` is, which is where a rename writes. Issue 4 is front matter whose closing line the worker and the editor read differently, so it carries no expected metadata. A sample the release already gives its expected metadata is left out, as issue 2's two samples are on 1.15.1. The forum issues where the reading view departs from CommonMark are spec examples, so they are in the spec files and not repeated.
- `editor-vs-reading-view-all.json`: every document of the editing mode oracle, 600 corpus documents (the first 40 of each of the 15 piece sets) and the judged samples, and the 14 forum issue samples, each with the three modes' HTML (`obsidianSourceModeHtml` and `obsidianLivePreviewHtml`, the editor's `.cm-content` as the user sees it, and `obsidianReadingViewHtml`), the worker's `CachedMetadata` and its `set`. It carries no judgement: a corpus document's views may agree or not.
- `editor-vs-reading-view-failing.json`: the notes on which the editor and Reading view read a note differently, each under its id in the `-all` file: the 14 samples of the forum issues (issues 5 to 12 of the summary sent to the team, and topic 50661, which had already reported its issue), each with its `forumUrl`, and one note for each new family the mode judge found ([`mode-judge.md`](mode-judge.md)), `issue: judged` with its `family`, each confirmed on the live editor's tree. Each has a one-sentence `note`, the three modes' HTML, `differsIn` naming the editing modes that disagree with Reading view (both, on every case, since both run the same parse) and the worker's `CachedMetadata`.

`src/oracle/spec/test-case-export.test.ts` pins that each full file holds every document of its oracle once, that the departures are the ones the spec suites explain, that the two spec failing files hold exactly the full files' cases the reading view departs on, 212 between them, that the no-spec files hold exactly the probes that differ from the reference, that the failing metadata file holds every worker document the worker throws on, each explained by a known trigger, and the forum files' counts, each editing mode case's three HTMLs against the oracle with one Source mode line per markdown line, that every failing editing mode case is in the `-all` file unchanged, and the expected metadata. `src/oracle/modes/editing-modes.test.ts` pins the parser to the editing mode oracle, the editor's classes and the worker's metadata on every document, and confirms each judged sample on the live editor's tree. `src/oracle/modes/forum-issues.test.ts` pins the parser to the forum issue oracle: the editor's classes and the worker's metadata on every document, and what 1.14.5 does with each of the owner's earlier reports (`OWNER_REPORT_SAMPLES`): front matter strings broken in Source mode only (topic 38294), no rule or image drawn in a `markdown` fence (topic 49620), Prism leaving `![](image.png)` plain there (topic 53597), bold styled there by design (topic 76476), and a callout in a nested list item carried onto the next item, which Live Preview draws inside the callout's embed (topic 80930, open as topic 57053). It found one gap, fixed with it: the editor closes front matter at `---` followed by spaces or tabs, and styles the whole line.
