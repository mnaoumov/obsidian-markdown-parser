# obsidian-markdown-parser

## L1. Status: PRIVATE

This repository is private. Do not make it public, publish it to npm, link it from any public place, or mention it in a public issue, PR, forum post or README of another project. Making it public needs the Obsidian team's permission first, and asking for it is the owner's call.

`npm run build` makes two installable packages, the whole parser and `obsidian-markdown-parser-metadata` (`packages/metadata/`, the metadata projection without the editor or CodeMirror dependencies), described in [`docs/api.md`](docs/api.md). Both keep `"private": true`: a consumer installs a tarball from `npm pack`, never a registry. A new module under `src/remark/` or `src/metadata/` stays inside the metadata package's import closure, which `src/entries/metadata-package.test.ts` pins; a new package that closure imports goes into `packages/metadata/package.json` at the root package's version.

## L2. Goal

A single incremental markdown parser for Obsidian-flavoured markdown, built on [`@lezer/markdown`](https://github.com/lezer-parser/markdown), that could one day serve both Obsidian's editor and its reading view. The Obsidian founder named Lezer as the target and the two hard parts (2026-10-13):

- **Live parsing** of a changing document: efficiency, partial states and resume points.
- **CSS-class compatibility**: today's editor uses a CodeMirror 5 token grammar, and themes and custom CSS depend on the classes it emits. The new parser must reproduce those class tokens exactly, or every theme breaks.

**Beyond Lezer (owner, 2026-10-13): compatible with all modern markdown parsers.** The Obsidian syntax (wikilinks and embeds, tags, `%%` comments, math, callouts, block ids, highlights, inline footnotes, task markers) is defined once, with one conformance corpus measured against Obsidian, and shipped as an extension for each ecosystem: Lezer (`@lezer/markdown`, the primary target), micromark + mdast (current unified/remark), and markdown-it. Each adapter is checked against the same corpus. Only the Lezer target also carries the editor's class-token compatibility layer. Scope confirmed by the owner (2026-10-13): all three, in that order - Lezer first, then micromark/mdast, then markdown-it.

## L3. Method: measured against the live app, never copied from it

- Behaviour is matched by differential fuzzing against a real Obsidian instance driven over CDP: the editor's class-token spans (read through `@codemirror/language`) and the metadata worker's `CachedMetadata`.
- Every oracle in `oracle/` is pinned to one Obsidian version, named once in `src/oracle/oracle-location.ts`. `npm run oracle:refresh` re-reads them all from another version and `npm run oracle:drift` reports what changed and whether the parser still matches ([`docs/oracles.md`](docs/oracles.md)). Moving the pin to a new version is a change of `PINNED_OBSIDIAN_VERSION` plus that version's files, once the drift report and the suites are clean on them.
- Obsidian's code is proprietary: never copy code from the app bundle into this repository. Reading it to learn behaviour is allowed for plugin development under Obsidian's Terms (Restrictions, item iii). What was read, what was only measured and what the oracle files hold are in [`docs/provenance.md`](docs/provenance.md); a part newly built from reading the app goes into its table.
- Open-source code the editor's behaviour descends from may be ported under its license, with the notice kept in [`THIRD-PARTY-NOTICES.md`](THIRD-PARTY-NOTICES.md). The class tokenizer ports the MIT CodeMirror 5 `markdown` mode and HyperMD, and uses CodeMirror 5's own sub-modes from `codemirror@5`.
- This work is the owner's own, done in his own time and never billed under his contractor agreement. It is intended as a gift to the Obsidian team, handed over with a written assignment if they take it into the core.

## L4. Phases

The phases below produced three engines rather than the single Lezer parser L2 names: the class tokenizer (`src/editor/`), the `@lezer/markdown` tree (`src/syntax/`) and the `remark-parse` 8 engine (`src/remark/`, `src/metadata/`). Why, and what one engine would take, is in [`docs/architecture.md`](docs/architecture.md).

0. Class-span oracle against the live editor; measure the gap between plain `@lezer/markdown` and today's tokens. Stop here if the CM5 tokenizer's quirks prove impractical to reproduce. **Done 2026-10-13: go, with a stateful mapping layer.** The numbers are in [`docs/phase-0.md`](docs/phase-0.md), and the harness is in `phase0/`: `oracle.mjs` reads the live editor's tree over CDP, `corpus.mjs` builds the documents, and `gap.mjs` scores a Lezer mapping against the oracle. It stays only to reproduce the Phase 0 numbers: Phase 1 replaced it with the TypeScript oracle below.
1. Obsidian syntax extensions plus a class-compatibility layer, driven to 0 diffs on fuzzed documents. **Class layer done 2026-10-14: all 46,508 documents in eleven oracle corpora exact, each with tables, HTML, 30 fenced languages, nested lists, markdown nested in markdown fences, code spans left open at the end of their line and highlight color markers.** The numbers, the rules the editor follows and what is left are in [`docs/phase-1.md`](docs/phase-1.md). The class layer is a line tokenizer with copyable state in `src/editor/`, resumable from any line, not a Lezer grammar, because the classes come from a line tokenizer. The oracle is `scripts/oracle.ts` (reads the live editor over CDP), `src/oracle/` (corpus and scoring) and `scripts/oracle-diff.ts` (scores and shows diffs); its corpora in `oracle/` are the test oracle of `src/editor/highlight.test.ts`. **Syntax extensions done 2026-10-14:** the Obsidian syntax is defined once in `src/syntax/spec.ts`, with a shared conformance corpus in `src/syntax/conformance.ts` and the `@lezer/markdown` extensions in `src/syntax/lezer.ts`. `scripts/syntax-diff.ts` scores the tree against the live editor's classes, construct by construct. The rules, the scores and the differences are in [`docs/syntax.md`](docs/syntax.md). **CodeMirror 6 host done 2026-10-14:** `src/editor/language.ts` runs the tokenizer as a CodeMirror 6 `Language` that gives the mode the next line, emits the editor's tree shape and resumes after an edit from the last chunk whose reads, lookahead included, end before it. **Reuse after the edit done 2026-10-22:** once a line past the edit ends in a state equal to the old parse's at the same text (`areLineStatesEqual`), it takes the old chunks from there on, so an edit at the start of 100,000 lines re-parses to the end in under 1 ms instead of 100 ms. `src/editor/view.ts` renders the classes. Design and cost (`scripts/cm6-bench.ts`) are in [`docs/cm6-host.md`](docs/cm6-host.md). **Demo plugin done 2026-10-22:** `src/demo-plugin/` is a private Obsidian plugin that runs the language as the editor's own, through the two node props Obsidian's renderer reads (`createEditorClassLanguage`'s `lineClassNodeProperty` and `tokenClassNodeProperty`), and compares it with the stock editor and metadata cache. On a real vault plus a 100,000-line note it gives 0 class and 0 metadata differences and a faster full parse. It also found three gaps, each made an item: some trees differed node for node (fixed 2026-10-22: the tree is now the editor's node for node on all 46,508 oracle documents, pinned in `src/editor/language.test.ts`, and on every note in the app), `parseMetadata`'s peak memory grew with the square of the note (fixed 2026-10-22: the engine put eaten text back as a concatenation that every later slice copied, and now 100,000 lines peak at 250 MB instead of 2.5 GB, and the comparison covers the long note too), and a live-preview keystroke on a long note cost three times the stock one (fixed 2026-10-22: live preview walks the whole tree on every change and splits every node's classes, so the re-parse now stops at the viewport's end, chunk reuse included, as `StreamLanguage`'s does, and the class strings are internalized; the keystroke now costs the stock one's). `scripts/build-demo-plugin.ts` builds it and `scripts/demo-plugin-measure.ts` runs it; the numbers are in [`docs/demo-plugin.md`](docs/demo-plugin.md). **Markdown blocks done 2026-10-14:** a block whose language resolves to the `markdown` mode runs the port without its editor layer, as Obsidian runs its fork of the CodeMirror 5 mode with the fork's default options. `src/editor/sub-modes.ts` registers the port as that mode. **micromark and mdast adapter done 2026-10-14:** `src/syntax/micromark.ts` is the syntax as a micromark extension and `src/syntax/mdast.ts` turns its tokens into mdast nodes. Both pass the whole corpus. On 29,596 oracle documents, 28,551 give the same Obsidian nodes as the Lezer tree (`scripts/adapter-diff.ts`), and the rest are places where the two parsers' block structure or delimiter pairing differs, listed in [`docs/syntax.md`](docs/syntax.md). **markdown-it plugin done 2026-10-14:** `src/syntax/markdown-it.ts` is the syntax as a markdown-it plugin, with tokens named after `ObsidianNode` and each token's source range in its `meta`. It passes the whole corpus, and 28,681 of the 29,596 oracle documents give the same Obsidian nodes as the Lezer tree (`scripts/adapter-diff.ts --adapter markdown-it`); the differences are in [`docs/syntax.md`](docs/syntax.md#the-markdown-it-plugin). The `codemirror` dependency is pinned to the CodeMirror 5 release the measured Obsidian bundles (5.64.0 for 1.14.4 and 1.14.5), because its sub-modes' classes differ between releases. **Spec suites done 2026-10-14:** every adapter takes one set of options, a preset (`commonmark`, `gfm`, `obsidian`) with any of its flags overridden (`src/syntax/options.ts`). With the `commonmark` preset, micromark and markdown-it pass all 652 examples of the vendored CommonMark 0.31.2 suite and the Lezer tree passes 651, rendered by `src/syntax/lezer-html.ts` with the fixes in `src/syntax/lezer-commonmark.ts`. The GFM extension examples, the examples still failing and what each flag changes are in [`docs/spec-suites.md`](docs/spec-suites.md). **Quirks measured 2026-10-14:** `scripts/spec-oracle.ts` reads every spec example from the live editor, metadata worker and reading view into `oracle/spec-obsidian-1.14.5.json`, and `src/oracle/spec-quirks.ts` explains each of the reading view's 211 differences from the spec, pinned by its test. Four quirks are flags of `ObsidianQuirkFlags` in every adapter, off in every preset: `setextHeading`, `emptyListItem`, `looseList` and `softLineBreak`. **More quirk flags done 2026-10-14:** `characterReference`, `autolink`, `htmlComment`, `htmlBlock`, `linkDefinition` and `gfmTable` in every adapter, and `listItem` in micromark and markdown-it; `@lezer/markdown` keeps list item continuation internal. Their rules follow `remark-parse` 8, which Obsidian's reading view and worker run (`src/syntax/quirk-rules.ts`), and the live app, on 101 probe documents that `scripts/quirk-probe-oracle.ts` reads into `oracle/quirk-probes-obsidian-1.14.5.json`, pinned by `src/oracle/quirk-probes.test.ts`. The rest, and why each is no flag yet, are in [`docs/spec-suites.md`](docs/spec-suites.md#obsidians-quirks). **Inline quirks decided 2026-10-14:** Obsidian's inline algorithm, tabs, lazy quote lines and paragraph whitespace are no flag of the three adapters. 68 more probes, read from the live app, show them, and stock `remark-parse` 8 with Obsidian's edits to three block tokenizers reproduces every parser difference measured, so they come by construction from a fourth parser built on it, which phase 2 needs too ([`docs/spec-suites.md`](docs/spec-suites.md#where-these-come-from-and-the-decision)). **The fourth parser done 2026-10-14:** `src/remark/` ports `remark-parse` 8.0.3 with Obsidian's edits to its `blockquote`, `list` and `table` tokenizers (re-expressed from their behaviour), `parse-entities` 2 and a `remark-html` 13 renderer. `parseRemark` gives its mdast tree, equal, positions included, to npm `remark-parse` 8 with Obsidian's tokenizers on 240,843 documents, and `renderRemarkHtml` gives the reading view's HTML on every example of the spec oracle's `quirk` rows but five the browser or the sanitizer changes after the parse, and on all 68 probes of the unflagged quirks, pinned in `spec-quirks.test.ts` and `quirk-probes.test.ts`. Details in [`docs/remark.md`](docs/remark.md). **The Obsidian syntax in the fourth parser done 2026-10-14:** `src/remark/obsidian.ts` adds front matter, internal links and embeds, tags, comments, math, highlights, footnotes with inline notes and block ids to the engine as tokenizers and tree transforms, with the metadata worker's rules, re-expressed from its behaviour. `parseRemark` gives the worker's nodes and positions on the worker oracle and the live app's metadata of every spec example, now checked through the phase 2 projection below. It gives the reading view's HTML on every example of the spec's syntax rows. The nine cases of the conformance corpus where the worker and the editor read the syntax differently are in [`docs/remark.md`](docs/remark.md#where-the-worker-and-the-editor-differ).
2. `CachedMetadata` projection from the same tree, checked against the metadata worker. **Done 2026-10-14:** `parseMetadata` (`src/metadata/`) gives the worker's whole `CachedMetadata`, equal as JSON, key order included: headings, internal links and embeds with the markdown links and images whose destination is no URL, tags, footnotes, link reference definitions, list items, sections, block ids, and front matter parsed by `yaml` 2 with its links, or `null` where the worker throws.
